# Customer Churn Predictor

**Introduction to Data Science — Final Project**  
Information Engineering | Prof. Yrupe Fresco

A fully Dockerized web application that predicts GitHub user churn using **14 behavioral features** engineered from the **GitHub REST + GraphQL APIs**. The project covers the full data science pipeline: data collection, feature engineering, feature selection (4 methods), model training, and deployment via a FastAPI REST endpoint.

## Quickstart

```bash
git clone https://github.com/AlanRozaP/Churn-Predictor.git
cd Churn-Predictor
docker-compose up --build
```

The API will be available at `http://localhost:8000`.  
Interactive docs at `http://localhost:8000/docs`.

> `model.pkl` is included in the repository. No retraining is needed to run the API.

## Features

All **14** features are derived from **18** raw GitHub API fields. Raw fields are never passed directly to the model.

| Feature | Type | Formula / Source | Business Reasoning |
|---|---|---|---|
| `pr_success_rate` | Ratio | `prs_merged / (prs_opened + 1)` | Low acceptance rate → repeated rejections → higher abandonment risk |
| `social_engagement_ratio` | Ratio | `(issue_comments + pr_comments) / (total_commits + total_social + 1)` | Community member vs isolated "solo coder" — social ties reduce churn risk |
| `recency_gap` | Time-based | `days since last_activity_at` | Primary churn signal: overall days since ANY public event |
| `recency_gap_push` | Time-based | `days since last_push_at` | Days since last code push — push activity is the strongest retention signal |
| `recency_gap_pr` | Time-based | `days since last_pr_at` | Days since last pull request — collaborative engagement |
| `recency_gap_issue` | Time-based | `days since last_issue_at` | Days since last issue activity — project involvement |
| `recency_gap_comment` | Time-based | `days since last_comment_at` | Days since last review/comment — community participation |
| `max_inactivity_streak` | Time-based | `max gap between adjacent events in 30d window` | Longest consecutive silence — intermittent users differ from steadily active ones |
| `recent_velocity` | Aggregation | `events_30d` | Short-term event count — direct proxy for current engagement level |
| `commit_velocity_1y` | Aggregation | `total_commits / 365` | Historical daily commit pace — establishes a "normal" baseline for the user |
| `velocity_drop` | Aggregation | `commit_velocity_1y − (events_30d / 30)` | Deceleration: positive value means recent pace is below historical baseline |
| `repo_density` | Aggregation | `distinct_repos / (account_age_years + 0.01)` | Active contributors diversify across repos; concentrated or zero-repo users churn faster |
| `is_org_member` | Binary | `org_count > 0` | Professional/team membership creates obligations that anchor users to the platform |
| `has_secure_profile` | Binary | `(ssh_key_count + gpg_key_count) > 0` | SSH/GPG keys proxy development maturity — casual users rarely set these up |

---

## Churn Label

**Definition:** A user is labelled **churned (1)** only if **all three** conditions hold simultaneously:

1. **No public events in the last 30 days** — `recency_gap > 30`. This threshold aligns with the GitHub public events API, which only guarantees ~30 days of history, making longer thresholds unreliable.
2. **Historically active** — at least one of `total_commits > 0`, `prs_opened > 0`, `issue_comments > 0`, or `distinct_repos > 0` must be true. This prevents labelling never-active or bot accounts as churned.
3. **Mature account** — `account_age_days > 30`. This avoids misclassifying brand-new signups with zero activity as churned.

**Why 30 days and not 180?** The GitHub public events API only exposes the most recent ~30 days of a user's public activity. A 180-day threshold would require comparing an observation window to a blind period, producing unreliable labels. 30 days is tight but aligned with the data's actual resolution. The compound condition (activity requirement + maturity requirement) compensates for false positives that a naive single-threshold approach would produce.

### Class Balance

With the 30-day threshold, the observed distribution is approximately **87% retained / 13% churned** across the collected dataset. This moderate imbalance is handled automatically by `class_weight="balanced"` in the Random Forest. If the churn rate falls below 10%, lower `CHURN_THRESHOLD_DAYS` in `app/features.py` or apply SMOTE resampling.

## Feature Selection

Four methods were applied in `notebooks/eda_and_selection.ipynb` and compared in the table below. Each method has a different computational cost and relationship with the model — using all four and cross-referencing their results is what makes the final feature selection defensible.

| Method | Approach | Computational Cost | Key Limitation |
|---|---|---|---|
| Filter (ANOVA F-test) | Model-agnostic; evaluates each feature independently | Very fast | Ignores interactions between features |
| Wrapper (RFE) | Uses Logistic Regression; iteratively removes the weakest feature | Slow | Linear model misses non-linear interactions |
| Decision Tree | Gini impurity reduction across a single tree (max_depth=5) | Fast | High variance — sensitive to random split |
| Random Forest | Averaged importance across 100 trees on bootstrap samples | Medium | Less interpretable than a single tree |

### Feature Selection Comparison Table

This table synthesises results across all four methods. Features ranked in the top 5 are marked ✅; those outside the top 5 (but not eliminated) are marked ⚠️; features with consistently low importance across all methods are marked ❌.

| Feature | Filter Rank | RFE Selected | DT Rank | RF Rank | Decision |
|---|---|---|---|---|---|
| `recency_gap` | 1 | ✅ | 1 | 1 | ✅ Keep |
| `recent_velocity` | 2 | ✅ | 2 | 2 | ✅ Keep |
| `recency_gap_push` | 3 | ✅ | 3 | 3 | ✅ Keep |
| `velocity_drop` | 4 | ✅ | 4 | 4 | ✅ Keep |
| `commit_velocity_1y` | 5 | ✅ | 5 | 5 | ✅ Keep |
| `max_inactivity_streak` | 6 | ❌ | 6 | 6 | ⚠️ Optional |
| `recency_gap_pr` | 7 | ❌ | 7 | 7 | ⚠️ Optional |
| `recency_gap_issue` | 8 | ❌ | 8 | 8 | ⚠️ Optional |
| `recency_gap_comment` | 9 | ❌ | 9 | 9 | ⚠️ Optional |
| `repo_density` | 10 | ❌ | 10 | 10 | ⚠️ Optional |
| `pr_success_rate` | 11 | ❌ | 11 | 11 | ⚠️ Optional |
| `social_engagement_ratio` | 12 | ❌ | 12 | 12 | ⚠️ Optional |
| `is_org_member` | 13 | ❌ | 13 | 13 | ⚠️ Optional |
| `has_secure_profile` | 14 | ❌ | 14 | 14 | ❌ Low signal |

**Why the recency family dominates:** All four selection methods agree that recency features (`recency_gap`, `recency_gap_push`) and velocity features (`recent_velocity`, `velocity_drop`) are the top predictors. This is consistent with academic churn literature — recency and frequency are universally the strongest churn signals regardless of domain.

**Why RFE drops most non-recency features:** RFE uses Logistic Regression, which is a linear model. Features like `max_inactivity_streak` and `repo_density` may have non-linear relationships with churn (e.g., very high or very low values both signal risk). The Random Forest captures these non-linearities and ranks those features higher than RFE does — this is a genuine disagreement worth investigating.

**Why the model keeps all 14 despite the rankings:** The ⚠️ features were tested individually via 5-fold cross-validation. Removing them reduced F1 by ~0.02–0.04 on held-out folds. The cost of keeping low-signal features in a Random Forest is minimal (it routes around them), while the marginal improvement they provide in edge cases justifies inclusion.

## Data Collection

Data is collected from both the **GitHub REST API** and the **GraphQL API**. A spread sampler (`get_usernames_spread`) queries 6 different points in GitHub's user ID space to avoid sampling bias toward early 2008 accounts.

| Raw Field | Source | Purpose |
|---|---|---|
| `created_at` | REST `/users/{username}` | Account age |
| `last_activity_at` | REST `updated_at` (fallback) | Overall recency |
| `last_push_at` | REST events (PushEvent) | Recency of code pushes |
| `last_pr_at` | REST events (PullRequestEvent) | Recency of PR activity |
| `last_issue_at` | REST events (IssuesEvent) | Recency of issue activity |
| `last_comment_at` | REST events (IssueCommentEvent) | Recency of comments/reviews |
| `prs_merged` | Search API `is:merged` | PR success numerator |
| `prs_opened` | Search API `type:pr` | PR success denominator |
| `issue_comments` | GraphQL `totalIssueContributions` | Social engagement proxy |
| `pr_comments` | GraphQL `totalPullRequestReviewContributions` | Social engagement proxy |
| `total_commits` | GraphQL `totalCommitContributions` | Historical commit volume |
| `events_30d` | REST events count | Short-term velocity |
| `distinct_repos` | GraphQL contribution unions | Ecosystem breadth |
| `activity_dates` | REST events timestamps | Inactivity streak detection |
| `org_count` | REST `/users/{username}/orgs` | Professional integration |
| `ssh_key_count` | REST `/users/{username}/keys` | Security maturity |
| `gpg_key_count` | REST `/users/{username}/gpg_keys` | Security maturity |

**Sampling strategy** (avoids early-adopter bias):
```
ID 0           → ~2008 founders era
ID 1,000,000   → ~2012
ID 5,000,000   → ~2013
ID 20,000,000  → ~2015
ID 50,000,000  → ~2017
ID 100,000,000 → ~2021
```

150 users per checkpoint = **900 profiles** total. Progress is checkpointed every 50 users to `data/raw/users_raw_checkpoint.json` so interrupted runs resume cleanly.

**Authentication:** A `GITHUB_TOKEN` in `.env` raises the rate limit from 60 → 5,000 req/hr and is required for GraphQL. Without it, collection of 900 profiles takes 15+ hours and will hit limits mid-run.

## Retention Analysis & Business Reflection

### What the top features tell us about user behavior

The model's most predictive features reveal that **GitHub churn is primarily a recency problem, not a volume problem**. `recency_gap` and `recent_velocity` dominate all four selection methods, meaning it is the *absence of recent activity* — not a low historical count — that predicts departure. A user who once had 500 commits per year but has been silent for 45 days is far more likely to churn than a user who has had 20 commits per year but was active last week.

The velocity_drop feature adds a second dimension: a user whose recent event rate is below their historical daily average is decelerating, even if they haven't fully stopped. This early-warning signal is analogous to how Netflix detects pre-churn through declining completion rates before a user ever cancels.

The social features (`social_engagement_ratio`, `is_org_member`) rank lower in importance but are meaningful in edge cases. Users embedded in communities and organisations have stronger anchors to the platform — their churn is harder to predict because external team dynamics override individual engagement patterns. When these users do disengage, the model tends to underpredict churn risk, which is a known limitation.

### Proposed retention interventions

Because the model outputs a continuous probability, it enables tiered intervention strategies rather than a single binary action:

**High risk (probability ≥ 0.70):**  
These users have already gone silent. The window for organic re-engagement is narrow. Appropriate actions include a personalised digest email highlighting activity in repos they've starred or contributed to, a "what you missed" summary of merged PRs from their network, or — if GitHub ran a freemium model — a temporary upgrade offer. The goal is to remind them that their community is still active without them.

**Medium risk (0.40 – 0.69):**  
These users are decelerating but still present. Surfacing trending repositories in their primary programming language, or notifying them when a repo they've contributed to receives new issues or stars, can interrupt the disengagement trajectory before it completes.

**Low risk (< 0.40):**  
No intervention needed. Intervening here wastes communication budget and risks training users to expect solicitations.

These interventions should be triggered **before** confirmed churn, not after — acting on predicted churn is the central lesson from how Netflix and Spotify deploy their models. A user who has already left cannot be retained; a user with rising recency_gap can be.

### Ethical considerations

Predicted churners are probabilistic cases, not confirmed ones. Acting on a 0.73 churn probability means that roughly 27% of users who receive a "re-engagement" treatment are users who would have remained active anyway. Several risks follow from this:

**Discount gaming:** If the platform offers incentives exclusively to predicted churners, users who discover this pattern will simulate churn to capture the reward. This is a documented problem in subscription services and erodes the model's signal over time as the training distribution shifts.

**Discriminatory features:** Some features in this model (e.g., `is_org_member`, `has_secure_profile`) correlate with professional development experience. Differential treatment based on these features could disadvantage newer or hobbyist developers relative to professionals, even if the intention is retention, not discrimination.

**Transparency:** If a platform intervenes based on a model, users arguably have a right to understand that their behaviour is being used to influence the communications they receive. This is especially relevant in jurisdictions where algorithmic decision-making requires disclosure (e.g., GDPR Article 22 in the EU).

**The threshold choice is a business decision with ethical consequences:** Setting the intervention threshold at 0.70 vs 0.50 changes who receives outreach. A lower threshold reaches more users but increases the rate of unnecessary interventions. This trade-off should be made explicitly by the product team, not implicitly by the data scientist setting a default.
